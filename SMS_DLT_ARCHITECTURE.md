# SMS and DLT architecture

All application SMS must be sent through `src/infrastructure/msg/sms` using a key from `SMS_TEMPLATE_KEYS`. Controllers and domain services must never compose complete SMS text or call APITXT directly.

```js
const { smsService, SMS_TEMPLATE_KEYS } = require("./infrastructure/msg/sms");

await smsService.sendTemplate({
  template: SMS_TEMPLATE_KEYS.LOGIN_OTP,
  mobile,
  variables: { otp, validityMinutes: 5 },
});
```

## Source of truth

- `sms.constants.js`: stable template keys, header types, and DLT categories.
- `sms.templates.js`: the only application location containing message bodies, variables, header selection, category, and environment-backed DLT template mapping.
- `sms.validator.js`: mobile, variable allowlist, and required DLT configuration validation.
- `sms.service.js`: provider-neutral application API and safe logging.
- `sms.provider.js`: APITXT adapter. A future provider is added here without changing business flows.
- `sms.config.js`: environment-backed provider and DLT configuration.
- `msg-otp.js`: compatibility facade retaining the existing Redis quota and static/live OTP behavior.

The text in `sms.templates.js` must be made identical to the final content approved in the DLT portal before enabling production delivery. Template IDs, PE IDs, headers, URLs, and credentials are deliberately absent from source control. Do not add telecom suffixes to headers unless APITXT/STPL explicitly requires them for the account.

## Delivery behavior

- OTP generation, storage, verification, resend cooldown, attempt limits, and daily quota continue to use the existing auth service and Redis keys.
- Mobile OTP delivery now selects a DLT key based on login, signup, password recovery, or mobile-verification purpose.
- Commerce SMS is queued through the existing BullMQ `notifications` queue. It runs only when `SMS_TRANSACTIONAL_ENABLED=true` and the recipient's existing notification preference has `sms: true`.
- Queue retries do not block order, payment, refund, or shipment requests.
- `SMS_ENFORCE_DLT=true` requires a PE ID, the selected approved template ID, and the selected approved header before a provider request is made.
- All currently defined application OTPs use `SERVICE` / `SERVICE_IMPLICIT`. `TRANSACTIONAL` support exists but is not assigned automatically; under Indian DLT guidance it should only be selected where legally applicable and approved.

## Configuration checklist

Copy the placeholder list from `.env.example`, obtain approved values from the STPL/APITXT account, and configure them in the deployment secret store. Keep `SMS_ENABLED=false` and `SMS_TRANSACTIONAL_ENABLED=false` until the approved content exactly matches the registry.

`SMS_OTP_API_URL` is the provider OTP endpoint. `SMS_API_URL` is the provider service/transactional message endpoint. They are separate because APITXT/STPL deployments can expose different endpoints.

## Existing system audit

- Authentication has password login, registration OTP, seller login OTP, buyer email/mobile OTP login-or-signup, resend OTP, forgot-password OTP, and reset-password verification.
- OTP values are generated by `shared/tools/otp.js` and stored in Redis with flow-specific TTL, cooldown, attempt, and daily quota keys.
- No separate change-mobile endpoint currently sends SMS; registry keys are ready for mobile verification and change-mobile flows when those existing APIs are introduced.
- Order, payment, cancellation, return/refund, and delivery modules publish domain events. Notification subscribers already create in-app/email notifications; SMS now uses those events rather than adding provider calls to business services.
- APITXT already handles Aadhaar/PAN/GST/bank verification, WhatsApp, and OTP. Those non-SMS-verification integrations remain unchanged.
- Logging uses Pino with OTP/token/password/API-key redaction. SMS logs contain only masked mobile numbers, template keys, categories, and provider request IDs.
- BullMQ and Redis provide queued delivery and retries. Existing HTTP rate limiting and auth-level OTP limits remain unchanged.

## Adding a template

1. Add a stable key in `sms.constants.js`.
2. Add one registry entry in `sms.templates.js`, including the exact approved content and variable order.
3. Add its placeholder environment name to `config/env.js` and `.env.example`.
4. Call `smsService.sendTemplate` or queue a `templated-sms` job with only that key and its declared variables.
5. Test with provider sandbox credentials before enabling production flags.
